## 读其他任何东西之前，先做这个检查

每一个会载入指令文件的 agent runtime —— `CLAUDE.md`、`AGENTS.md`、Cursor rules、`copilot-instructions.md`、Assistants 的 `instructions` 字段 —— 都有大小上限。多数在超限时**静默截断**。

用 runtime 量度的方式去量你自己的文件：

```bash
# runtime 实际计算的（UTF-16 code unit）
node -e "console.log(require('fs').readFileSync('CLAUDE.md','utf8').length)"

# 你多半是这样检查的（UTF-8 字节）
wc -c CLAUDE.md
```

如果两个数字差很远，代表你的文件不是纯 ASCII，而**你一直信任的两个量度之中，有一个是错的**。中文、日文、韩文的差距是 1.8–2.1 倍：一个 CJK 字符占 1 个 UTF-16 unit，却占 3 个 UTF-8 字节。

我们把这件事搞错了两个月。代价是一场虚构的紧急事故，以及一个由四个模型组成、一致得出错误结论的审查小组。摘要在[下方](#我们错在哪里)。

📄 **完整设计论述 —— 概念、设计决定，以及如何套用到任何 runtime —— 见 [Compiling agent identity](docs/compiling-agent-identity.md)（英文）。**

## 问题

一个能干的 agent 需要大量常驻指令：它是谁、如何说话、绝不可违反的规则、可用的工具、可以假定为真的事实、良好行为的实例。这些全部必须**每一轮都在场**，所以全部塞进 runtime 启动时载入的文件里。

这些文件只会长大。没有人会删掉一条规则。而且没有任何工作流程中的步骤会问一句：**「什么东西不属于这个文件？」**

于是你逐渐逼近上限。然后越过。然后 runtime 悄悄丢掉你 agent 的一部分指令 —— 而 agent 自己毫不知情。它无法告诉你它的反捏造规则不见了，因为那条本该令它谨慎的规则，正是被切掉的那一条。

这不是假设。我们就是这样失去一个 agent 的护栏，换来一个自信满满的捏造答案：捏造的日期、捏造的法案、捏造的票数，没有来源，没有查证。

## Soul Compiler 做什么

它把一份冗长的、人手撰写的角色规格，编译成 agent 实际载入的精简运行身份，并且明确地、有纪录地决定：什么留在文件内，什么移出去。

```
COMPOSE     trait card + 配置文件      → 组装草稿
REVIEW      LLM 通读整份 soul          → 判断
CLASSIFY    每个区块得到唯一分类        → 确定性 taxonomy
MAP+INJECT  按类别路由到文件            → soul 只保留指针
```

分工是刻意的：**模型负责审阅与标签，普通代码负责路由与写入。** 模型永远不挑文件路径，永远不碰磁盘。需要判断的地方交给判断，其余一律确定性。

## 2.0 架构 —— BEING 对 KNOWING

令预算问题变得可解的洞察是：常驻指令其实是两种不同性质的东西。

|  | BEING（我是谁） | KNOWING（我知道什么） |
|---|---|---|
| 内容 | 身份、语气、铁律 —— 令这个 agent 成为「这个」agent 的东西 | 共享规则、工具纪律、参考事实、程序、范例 |
| 性质 | 稳定、有界、每个 agent 独有 | 无限增长，通常整个 fleet 共享 |
| 路由 | **留在文件内** | **抽出去** —— 身份文件只留一个指针 |

BEING 很小，而且会一直小。真正会长大的是 KNOWING，而它根本不需要住在身份文件里。把两者分开，文件就不再朝上限漂移，因为会长大的那一半已经搬到别处。

这个机制毫不炫目，而这正是重点：多数 runtime 本来就会载入好几个指令文件，每个文件各有自己的预算。把内容分布到 runtime **本来就会读**的文件，胜过发明一个新的载入器。

分类是内容哈希锁定的。每个区块的路由决定都钉死在其文字的哈希上，所以重跑编译器是确定性的；而任何会把内容移出身份文件的决定，都需要人手批准。分类不确定时一律倾向留在文件内 —— 静默的内容遗失才是危险方向，所以模棱两可一律判给「不抽出」。

## 我们错在哪里

两个月前，我们用 `wc -c` 记录每个 soul 文件的大小，然后拿去跟一个以 UTF-16 code unit 计算的上限比较。此后追踪的每一个数字，都被膨胀了 1.8–2.1 倍。

后果并不细微：

- 我们相信某个 agent 处于**上限的 161%、正在截断中**。实际是 83%。
- 我们相信 7 个 agent 之中有 5 个每轮都在流失内容。一个都没有。
- 我们计划紧急改配置去调高上限。那什么都解决不了。
- 我们召开审查小组 —— 一个独立实现者、两个来自不同实验室的独立模型、加一个主持 —— 去决定该做增量发布还是重新奠基。**四个都同意。四个都错**，因为四个读的是同一份简报，而简报里带着那个单位错误。

只有对抗式的 checker 抓到了，而且只因为它亲自对磁盘重新量度，而不是从文件推理。

从中值得带走三件事：

**当所有人共用同一个输入，共识并不构成佐证。** 推理层的独立性一文不值，只要输入层存在同一个缺陷。如果结论建基于某个量度，那么应该有一位审查者的职责是**重新推导那个量度**，而不是在它之上重新辩论逻辑。

**我们连截断的几何形状都搞反了。** 我们针对的 runtime 保留的是**前 75% 与后 25%**，切掉的是中间。我们一直以为它切尾。放在文件最末端的东西其实相对安全；脆弱的是中段。

**问题其实早已解决。** 多文件拆分在恐慌爆发前数周就已上线。6,417 个 session 纪录之中，只有 2 个含截断警告 —— 两个都在拆分之前，之后为零。我们是在用错误的单位读陈旧的数字，然后把它误认为一场正在烧的火。

正确量度后，一个七 agent fleet 对 12,000 unit 上限：

| Agent | 身份文件 | 占上限 |
|---|---|---|
| A | 10,656 | 89% |
| B | 9,931 | 83% |
| C | 8,026 | 67% |
| D | 7,764 | 65% |
| E | 6,168 | 51% |
| F | 5,605 | 47% |
| G | 5,010 | 42% |

每个文件都放得下。一个值得留意。没有东西在烧。

## 工具

这场检讨产出三个小工具，即使你不编译任何东西也用得上：

| 工具 | 作用 |
|---|---|
| `bootstrap-headroom` | 以 runtime 自己的单位，量度它实际载入的指令文件，并在你撞到上限**之前**发出警示，而不是之后。 |
| `deploy-diff-gate` | 当线上环境持有你的源头没有的内容时，拒绝部署 —— 拦截那些在生产环境手改、而重新生成会静默摧毁的内容。 |
| `soul-version` | 为编译后的身份铸造一个稳定、内容寻址的版本号，让你分辨得出是哪一块棱镜产生了哪一种行为。 |

`deploy-diff-gate` 上线即回本：它在整个 fleet 找出 124 行只存在于生产环境的内容，其中包括一条全 fleet 适用的反捏造规则 —— 下一次部署就会抹掉它，而那正是上文事故中被切掉的同一类护栏。

`soul-version` **刻意排除**模型识别码。**Soul 是棱镜，模型是光。** 把 agent 换到另一个模型不可以改变它的身份，否则你就再也无法把行为差异归因于角色而非引擎。

## 诚实的适用范围

- **已运作、已在生产：** 编译管线、带哈希锁定路由的分类、共享内容的 fleet 级去重、多文件拆分，以及上述三个工具。229 个测试通过。
- **目前围绕单一 runtime 成形。** 文件名、12,000 unit 上限、workspace 布局都跟随 OpenClaw 的惯例。概念可以干净移植，代码还不行。可插拔的 target profile 是下一件工作 —— 在它落地之前，这份东西的价值在于阅读多于安装。
- **不是提示词优化器。** 它不会令你的 agent 更聪明。它决定你的 agent 带着什么，并且证明没有东西掉出去。

## 先量度，再相信

如果你只从这个 repository 带走一件事，带走最上方那个检查。拿它去跑你自己的指令文件。

真正的失效模式不是上限太苛刻，而是越限是**静默的**，而且最直觉的检查方式，会用错误的单位回你一个错误的数字。
